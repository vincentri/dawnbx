title: Install
description: Get dawnbx onto a Linux server, AWS, or a local VM.
---

One installer sets up everything: k3s, the API server, the dashboard, and
TLS. Run it on a clean Linux box.

## On a Linux server

```sh
sudo ./install.sh --domain sb.example.com   # Let's Encrypt; DNS must point here, ports 80+443 open
sudo ./install.sh                           # no domain: HTTPS with a self-signed cert
sudo ./install.sh --local                   # laptop/VM: HTTP on 127.0.0.1:8080 only
```

When it finishes, the installer prints `DAWNBX_URL`, `DAWNBX_API_KEY`, and the
dashboard login (user `admin` plus a generated password). It also saves the URL
and key to `~/.dawnbx/env`, which is what the CLI and SDKs read.

Run `./install.sh --help` for the full flag list.

### Choosing the admin password

To pick it yourself:

```sh
sudo DAWNBX_ADMIN_PASSWORD=... ./install.sh
```

Lost it? Put a new one in `/var/lib/dawnbx/server/admin.env`:

```
DAWNBX_ADMIN_PASSWORD=...
```

Read as-is, no quoting, then `systemctl restart dawnbx`. A password changed in
the dashboard survives restarts until that line changes.

### Lost the API key

Make a new one in the dashboard under **Settings**, or re-run the installer:

```sh
sudo ./install.sh --new-key
```

The old key stops working.

### Headless installs

Run it without a terminal (cloud-init, CI) and it prints the *paths* of the key
and password files, never the secrets themselves. Read them over SSH.

## As a control plane

`install.sh` gives you **one box that runs sandboxes**. That is the whole of
every section above.

The other mode is `dawnbx-server --control-plane`: the same dashboard, API and
database, but it manages *clusters* instead of running sandboxes, and has no
cluster and no sandbox volume of its own. You point it at a cloud, and it
provisions a k3s host per cluster from the dashboard. It is the mode to use if
you would rather not provision a box by hand.

```sh
sudo dawnbx-server --control-plane \
  --listen 127.0.0.1:8080 \
  --region eu-west-1 \
  --release-url https://example.com/dawnbx \
  --template /opt/dawnbx/deploy/aws/dawnbx.yaml \
  --admin-password "$DAWNBX_ADMIN_PASSWORD"
```

The flags it needs:

| Flag | |
|---|---|
| `--control-plane` | run as a control plane. Without it the same binary refuses to start without a cluster and a mounted data volume |
| `--region` | the region to provision clusters in |
| `--release-url` | HTTPS base serving `install.sh` and the release binaries, so a provisioned cluster can install itself. There is no public release yet, so you host one |
| `--template` | path to the CloudFormation template used to create a host. Empty reads `deploy/aws/dawnbx.yaml` **relative to the working directory**, so run the binary from a checkout or pass the path |
| `--admin-password` | the dashboard login. Defaults to `$DAWNBX_ADMIN_PASSWORD`, then `admin.env`, then a generated one |
| `--control-plane-key` | 32 bytes that encrypt cluster credentials at rest. Generated once into `<data-dir>/server/control-plane.key` if unset; set it to keep that file across rebuilds |
| `--key-pair`, `--ssh-cidr` | **rescue access only** — an EC2 key pair and the CIDR allowed to SSH a provisioned host. The normal path needs neither: the administrator password is injected through the cloud's secret store and the API key is minted by the cluster itself. A control plane without them starts and provisions, but a host whose normal path has failed is a host you cannot reach |

**You sign in as an administrator.** The control plane creates one dashboard
user — `admin`, or whatever `$DAWNBX_ADMIN_USER` names — and it is an admin,
because every cluster route but the capability probe and the provider list
refuses a member. A member account can be added under **Settings > Users**, but
on a control plane all it can do is read its own keys; the Clusters page tells
it so.

**Phase one is one AWS account and one credential source.** The control plane
takes credentials from the standard AWS chain — environment, shared config or
SSO, or a web identity — and uses that one source for every cluster it
provisions. There is no per-cluster credential, and no way to point one cluster
at one account and another at a different account. A lapsed credential does not
stop the control plane: it starts, lists the clusters it already has, and shows
the provider as listed-but-unavailable.

To add a cluster: open the dashboard, choose AWS, pick a region and a size,
review the estimate, and confirm. You get back the cluster's URL, its API key
and its administrator password — no SSH, and nothing to read off a host.

## On AWS

`deploy/aws/dawnbx.yaml` is a CloudFormation stack: one arm64 EC2 instance
(t4g.medium by default) with an Elastic IP and HTTPS on `<ip>.sslip.io`, or on
your domain.

Create it in the console (**Create stack > Upload a template**) and fill in:

- the key pair,
- your IP for SSH,
- `ReleaseUrl`: the base URL of a [release](https://github.com), since there is
  no public release yet — you host one yourself for now.

The stack finishes when the installer does, about 5 minutes. The `SshCommand`
output then prints the API key and admin password.

The template has not been launched yet. If you already have a Linux box, run
`install.sh` on it instead — that path is exercised by the dev VM.

- `CpuCredits` defaults to `standard`: the price stays fixed, but CPU slows down
  once burst credits run out. `unlimited` stays fast and bills the extra.
- If creation fails, re-create it with rollback disabled ("Preserve
  successfully provisioned resources"). Then SSH in and read
  `/var/log/cloud-init-output.log`.
- Workers: launch them into the stack's `SecurityGroup` output, then run the
  [join command](/docs/guide/nodes).

## On a Mac

[Lima](https://lima-vm.io) runs it in a Linux VM:

```sh
brew install lima
hack/dev-vm.sh                      # ~10 min the first time; re-run to upgrade
hack/dev-vm.sh dawnbx --new-key    # print a fresh key (old one stops working)
```

The script copies the VM's `~/.dawnbx/env` to the Mac, so the CLI and SDKs work
from the host against `http://127.0.0.1:8080`.
